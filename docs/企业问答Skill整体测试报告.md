## 3. 判定方法

本轮不是只跑 FakePlanner，而是使用真实链路：

```text
自然语言问题
  -> LLM 生成 QueryPlan
  -> validate_plan 校验和归一化
  -> DB / KB / Hybrid 执行
  -> LLM 润色或 fallback 答案
  -> 人工复核答案要点和来源
```

判定标准：

- “通过”：答案包含核心事实，查询来源合理，未捏造关键事实。
- “风险通过”：答案可接受，但存在重跑不稳定、证据未完全核实、或依赖用户前提的问题。
- “未通过”：无法回答官方要求、路由错误、使用错误规则、或缺少必要查询能力。

## 7. 失败与风险归因

### 7.1 T09：不存在员工查询没有默认字段兜底

问题：

```text
查一下 EMP-999
```

实际行为：

```text
PlanValidationError: 缺少必要参数：field
```

原因：

- `employee_basic` 要求 `field` 必填。
- LLM 对“查一下 EMP-999”只提取了 `employee_id`，没有补 `field: name`。
- validator 正确拦截了不完整计划，但最终行为没有达到“明确告知无此员工”的测试预期。

建议：

- 对 `employee_basic` 增加默认字段：当只有员工定位参数时，默认 `field = "name"`。
- 或新增 `employee_lookup` 模板，用于“查一下某人/某员工 ID”的概览查询。

### 7.2 A05 / B13：会议纪要 KB 检索稳定性不足

问题：

```text
3 月全员大会说了什么？
今年有调薪计划吗？
```

现象：

- A05 只命中会议头部，没有召回议程、组织调整、Q&A 等核心内容。
- B13 首次批量测试未命中调薪 Q&A，复跑时命中并回答正确。

原因：

- 当前 KB 检索按 Markdown heading 切块，查询命中文档标题后，不一定带出同一文档的后续章节。
- LLM 改写 query 后，关键词召回可能不稳定。

建议：

- 当命中会议标题或文档标题时，追加同一文件的相邻章节或整篇短文档摘要。
- 对会议纪要增加轻量元数据：日期、会议名、议程、Q&A。
- KB 检索可增加“文件级召回 + 章节级重排”两段式策略。

### 7.3 B08：晋升判断 formatter 固定为 P5→P6 规则

问题：

```text
张三 P6 晋升 P7 可以吗？
```

实际行为：

- 证据中包含 `promotion_rules.md section P6 → P7`。
- 答案却使用了 P5→P6 的判断口径：连续 2 季度 KPI≥85 或年度平均≥85、主导/核心参与项目≥3。

原因：

- `promotion_eligibility` 的事实检索能取到 `from_level/to_level`。
- 但 fallback formatter 中晋升规则判断逻辑仍写死为 P5→P6。

建议：

- 明确当前只支持 P5→P6，并对其他晋升级别返回“不支持该晋升规则自动判断”。
- 或把晋升规则结构化，按 `from_level/to_level` 选择不同 check list。

### 7.4 B10：一个问题拆多查询的能力不足

问题：

```text
王五上个月迟到超过扣款线了吗？
```

预期需要：

```text
查王五 2026-02 迟到次数 -> 查迟到扣款规则 -> 综合判断
```

实际行为：

- 一次运行返回澄清。
- 一次运行 LLM 生成了 `sub_queries`，但 validator 拒绝，因为当前 QueryPlan 不支持该参数。

原因：

- 当前模板支持 `attendance_stats` 和 `kb_search`，但没有 `attendance_policy_check` 这类混合模板。
- QueryPlan 是单模板执行，不能表达“一问多查再合成”。

建议：

- 不建议开放任意 `sub_queries`。
- 可以新增受控模板：`attendance_policy_check`，参数包括员工、时间范围、考勤状态、政策类型。

### 7.5 B16：特殊员工名 `CEO` 被当作未知实体

问题：

```text
CEO 的邮箱是多少？
```

实际行为：

```text
请问CEO的姓名或员工ID是什么？
```

原因：

- LLM 把 CEO 当作职位或模糊称谓，没有映射到员工表中的 `name = CEO`。

建议：

- 在 planner prompt 的字段映射示例中加入 `CEO` 作为可查询员工名。
- 或在 validator/executor 前做轻量实体探测：若问题包含明确员工表中的 name，可优先按员工处理。

### 7.6 B18：两跳查询缺少模板支持

问题：

```text
张三的直属上级的邮箱是多少？
```

实际行为：

```text
张三的直属上级是CEO，但该记录中未提供CEO的邮箱。
```

原因：

- `employee_manager` 只返回 manager name 和 manager_id。
- 答案层不能继续拿 manager_id 查 email。

建议：

- 增加受控模板 `employee_manager_contact`。
- 或扩展 `employee_manager` 的 allowed select，安全返回 `manager_email`。

## 8. 对当前实现的评价

### 做得好的部分

- QueryPlan + QueryTemplate 的受控执行方向是对的，没有让 LLM 直接生成 SQL。
- SQL 注入类问题能被拦截。
- 项目状态别名和多状态过滤已经稳定。
- P5→P6 晋升判断对官方用例可用，且能合并 DB 和晋升规则文档。
- 空结果多数情况下能明确说“没有找到”，没有明显编造。
- 来源标注整体完整，DB 表和 KB 文档都能追溯。

### 需要收敛的部分

- 不要继续无限补自然语言别名。更应该补模板能力和检索策略。
- 对“未知但可澄清”的问题，要区分“需要用户解释概念”和“数据源没有该字段”。
- 对跨多个模板的问题，需要新增少量受控混合模板，而不是开放万能子查询。
- 对 KB 命中文档标题的情况，需要扩大召回上下文，否则会议纪要类问题容易只拿到标题块。

## 10. 最终建议

当前版本已经能覆盖大多数公开测试和同类泛化问题，可以作为可演示版本提交。但若目标是面试现场更稳，建议至少先修复：

1. T09 员工概览兜底。
2. A05 会议纪要召回。
3. B08 晋升规则级别选择。
4. B10 考勤制度混合判断。
5. B18 上级联系方式两跳查询。

这 5 项修复后，系统会从“官方样例基本可过”提升到“面对面试官追问也比较稳”的状态。
